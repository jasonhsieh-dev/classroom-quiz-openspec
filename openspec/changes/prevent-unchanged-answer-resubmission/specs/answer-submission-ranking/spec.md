# Spec Delta

## MODIFIED Requirements

### Requirement: 接受每組每題的有效提交
系統 SHALL 在活動為 `OPEN`、session 組別合法、題目屬於活動且答案去除前後空白後非空時接受首次提交或內容真正變更的新提交；與該組該題目前有效答案相同的新請求 SHALL 依未變更規則處理。系統 MUST 以 session 綁定組別作為提交者，並 MUST 拒絕不符合既有驗證條件的提交而不改變有效答案。既有成功請求的冪等重送與衝突語意 MUST 保持不變。

#### Scenario: 提交第一個有效答案
- **WHEN** 有效學生 session 在 `OPEN` 活動對現有題目提交非空答案，且該組該題尚無有效提交
- **THEN** 系統接受答案、記錄伺服器接收資訊，並將它設為該組該題的目前有效提交

#### Scenario: 提交空白答案
- **WHEN** 學生提交空字串或僅包含空白字元的答案
- **THEN** 系統拒絕提交並回傳驗證錯誤，且不建立新的有效提交

#### Scenario: 提交不存在的題目
- **WHEN** 學生提交不屬於目前活動的題目識別碼
- **THEN** 系統拒絕提交，且不建立提交歷程

### Requirement: 修改答案建立新歷程
系統 SHALL 僅將同組同題後續答案經既有 `trim()` 正規化後與目前有效答案精確不同的有效新提交視為修改，新增不可變的提交歷程，並將目前有效提交指向最新紀錄。修改 MUST 更新該組該題的有效伺服器接收時間；舊紀錄 MUST 不參與最終順位。比較 MUST 只針對目前有效答案，不得因歷史上曾提交相同內容而阻止合法修改。

#### Scenario: 學生修改已提交答案
- **WHEN** 學生在 `OPEN` 活動對已作答題目提交與目前有效答案不同的新有效答案
- **THEN** 系統保留舊歷程、建立新歷程，並以新答案及新接收資訊取代目前有效提交

#### Scenario: 修改造成順位下降
- **WHEN** 原本較早提交的組別在其他組提交後修改答案
- **THEN** 該組使用修改後的接收資訊重新排序，且不保留第一次提交的較前順位

#### Scenario: 改回歷史答案
- **WHEN** 同組同題依序以不同新 key 提交 A、B、A，且每次都符合既有驗證條件
- **THEN** 三次皆為合法新提交，各自建立歷程與接收資訊，最後一次不恢復第一次的接收序號或順位

## ADDED Requirements

### Requirement: 相同有效答案不產生新提交
系統 MUST 在序列化的提交交易內、配置新接收序號之前，將本次 `trim()` 後答案與同組同題目前有效答案精確比較。通過既有驗證且未命中既有成功 key 的請求若答案相同，系統 SHALL 回傳 `409 ANSWER_UNCHANGED` 與「答案未變更，無須重新提交」，不得建立 attempt、改變 current submission、receive_sequence、下一接收序號、revision、serverReceivedAt 或順位，也不得觸發 `submission.updated`。學生端 SHALL 將該回應顯示為一般提示。

#### Scenario: 新 key 提交相同答案
- **WHEN** 學生在 OPEN 活動以新 key 提交與同組同題目前有效答案相同的內容
- **THEN** 系統回傳未變更回應，所有有效提交資訊與歷程數量保持不變，學生端顯示指定提示

#### Scenario: 僅前後空白不同
- **WHEN** 本次答案與目前有效答案僅有既有 `trim()` 會移除的前後空白差異
- **THEN** 系統判定未變更；不額外折疊內部空白、忽略大小寫或進行其他文字正規化

#### Scenario: 不同組提交相同文字
- **WHEN** 不同組別對同一題分別首次提交相同文字
- **THEN** 各組依原規則建立自己的有效提交、接收序號與時間，不互相去重

#### Scenario: 同組不同 session 提交相同答案
- **WHEN** 同組另一個合法 session 以新 key 提交與該組該題目前有效答案相同的內容
- **THEN** 系統同樣回傳未變更，不因 session 不同建立新 attempt

#### Scenario: 兩個相同答案請求並行
- **WHEN** 同組同題尚無答案或目前答案不同，兩個合法請求以不同新 key 並行提交相同新答案，包括來自同組不同 session 的情況
- **THEN** 最多一個請求建立新 attempt，另一個在取得寫入順序後讀取更新的有效答案並回傳未變更；只增加一次接收序號與 revision，也只產生一次提交更新事件

#### Scenario: 既有成功 key 的重送與衝突優先
- **WHEN** 請求使用已成功建立 attempt 的同 session、題目與 key
- **THEN** 正規化答案相同時回傳該次原結果，即使目前答案已變或活動已截止；內容不同時依原規則回傳 IDEMPOTENCY_CONFLICT，不改動有效提交

#### Scenario: 截止後以新 key 提交相同答案
- **WHEN** 截止交易先取得寫入順序，隨後學生以新 key 提交與目前有效答案相同的內容
- **THEN** 系統仍回傳 ACTIVITY_CLOSED，不以 ANSWER_UNCHANGED 或成功回應取代截止拒絕

#### Scenario: 未變更回應不建立成功 key 紀錄
- **WHEN** 新 key 因答案相同而收到 ANSWER_UNCHANGED
- **THEN** 系統不將該 key 記錄為成功提交；其後請求仍依當時活動狀態、目前有效答案與既有驗證規則處理

# 課堂搶答系統人工驗收清單

## 驗收準備

- [ ] 執行 `npm ci`、`npx playwright install chromium`、`npm run dev`。
- [ ] 健康檢查回傳 `status: ok`。
- [ ] 在同一瀏覽器 profile 開啟老師頁與一個學生頁，另開一個隔離學生 context；需要驗證同組多 session 時再開第三個隔離學生 context。
- [ ] 同一個一般瀏覽器 profile 只代表一個學生 session；若同時測試不同組學生，第二組 MUST 使用無痕視窗或另一個 browser profile。一般視窗的多個學生分頁會共用 student cookie，系統應拒絕身分已被其他分頁切換的舊分頁提交，且不得新增 submission attempt。
- [ ] 使用 `tests/fixtures/guided-notes/reference-single-template.xlsx`；不得使用真實學生資料。

## 老師匯入與建立活動

1. 老師上傳 XLSX。
   - 預期：顯示 6 題、各題題號、工作表、動態答案範圍及原內容警告。
   - 通過：沒有固定儲存格假設，也沒有在確認前建立活動。
2. 老師按「確認並建立活動」，記下畫面顯示的活動識別碼。
   - 預期：出現 `DRAFT` 活動、活動識別碼與組別管理。
3. 在「組別數量」輸入 `6` 並按「建立組別」。
   - 預期：單次操作顯示「第 1 組」至「第 6 組」完整清單，不需要逐組輸入名稱；請求期間按鈕停用，不會因重複點擊累加組別。
   - 邊界：輸入 `0`、`101` 或非整數時顯示 1–100 整數驗證錯誤；輸入 `1` 可保存草稿，但「開始搶答」維持停用並提示至少需要兩組。
   - 重設：尚無學生 session 時可確認後重新產生完整清單；確認取消時原清單不變。
4. 使用學生頁在 `DRAFT` 選擇「第 1 組」，再由老師嘗試重新產生組別。
   - 預期：系統明確拒絕重設；原組別 ID、學生 session 綁定與完整清單都不變。
5. 老師按「開始搶答」。
   - 預期：活動變成 `OPEN`，所有題目同時開放，組別不能再修改。

## 老師活動恢復與狀態標題

6. 在 `DRAFT` 活動頁記錄 URL、活動識別碼與目前組別清單，重新整理瀏覽器。
   - 預期：URL 仍為 `/teacher/activities/:activityId`，主標題為「設定搶答活動」，活動名稱獨立顯示，原題目與組別設定均由後端 snapshot 恢復；不會再次確認匯入或建立活動。
7. 開始活動成為 `OPEN`，完成至少一筆學生提交後重新整理老師頁。
   - 預期：主標題為「搶答活動進行中」，恢復同一活動的題目、目前提交、revision 與「結束活動」操作。
8. 結束活動成為 `CLOSED` 後重新整理老師頁。
   - 預期：主標題為「活動結果與匯出」，顯示相同最終結果，且「下載已回填 Guided Notes」仍可再次下載 XLSX。
9. 回到老師根頁，確認沒有 `OPEN` 時同時看見匯入入口及既有 `DRAFT/CLOSED` 清單，再明確選擇其中一場歷史活動。
   - 預期：系統只載入選擇的 activity；不任意恢復其他歷史活動，也不自動建立或確認重複活動。若存在唯一 `OPEN`，根頁則自動導向該活動。
10. 直接輸入不存在的 `/teacher/activities/:activityId`，並各測一次 session 建立失敗與 snapshot API 失敗。
    - 預期：顯示清楚錯誤、載入／重試或返回活動清單操作，不顯示可誤操作的活動內容。

## 多組學生與隱私

11. 兩個學生 context 輸入同一 `activityId`，分別選擇「第 1 組」、「第 2 組」。
   - 預期：各自建立 HttpOnly session 並看到全部題號。
   - 防誤用：先在同一個一般瀏覽器 context 開兩個學生分頁並依序選不同組；回到前一分頁提交時，預期顯示組別 session 已在其他分頁變更、本次提交未保存，並提示使用無痕視窗或不同 browser profile。
12. 兩組近乎同時提交第一題；再分別提交第二、第三題。
   - 預期：老師即時看到兩組名稱、答案及時間；學生只看到自己組別資料。
13. 第 2 組修改第一題答案並確認。
   - 預期：老師看到新答案與新時間；舊歷程保留但不再是有效答案。
14. 另開學生 context 再選「第 1 組」，修改第 1 組第二題。
   - 預期：系統允許同組多個 session；原第 1 組畫面經 socket 通知或重連 snapshot 顯示同組最新答案。
15. 在兩個不同組別的學生 Network 檢查 `snapshot`。
   - 通過：不含其他組答案、提交狀態、時間、`receiveSequence` 或暫時順位。
16. 嘗試以第一場學生 session 查詢另一活動 snapshot。
    - 通過：伺服器回覆 403，URL、query 或 body 竄改不能改變 session 綁定組別。

## 重連、冪等與截止

17. 將第一組 context 暫時離線，由同組另一 session 修改答案，再恢復連線。
    - 預期：重連後重新抓 HTTP snapshot，顯示最新答案；不依賴事件重播。
18. 對同一題用相同 idempotency key 與相同答案重送兩次。
    - 通過：兩次回應相同，沒有新增有效提交、接收序號或 revision。
19. 老師按「結束活動」並接受確認，請求期間再次嘗試點擊。
    - 預期：按鈕顯示「結束中…」且停用，只送出一個 close；成功後切換唯讀結果。
20. 截止後送出延遲提交或修改 API。
    - 通過：伺服器回覆 409，資料與結果不變。

## 結果與匯出

21. 老師查看結果。
    - 預期：每題顯示成功組別及所有組別的順位、答案、伺服器時間；沒有判分或遞補操作。
22. 兩組學生查看結果。
    - 預期：只顯示各題成功組別名稱／識別碼，以及本組答案與順位；成功組別不是自己時，也看不到其答案、時間或順位欄位。
23. 老師按「下載已回填 Guided Notes」。
    - 預期：瀏覽器下載新的 `.xlsx`，來源檔沒有被覆蓋。
24. 比較來源與匯出檔。
    - 通過：第一名最後有效答案寫入動態 answer anchor；無成功組別保留原值；所有工作表及順序、非目標值／公式、格式、合併範圍、列高、欄寬、工作表／列／欄隱藏狀態完全一致。

### 2026-10-27 真人驗收發現：同 profile 多學生分頁

使用者以同一個 Chrome／Edge 一般視窗開啟多個學生分頁，分別選擇不同組別後，發現舊分頁仍顯示原組別名稱，但其後提交依共用 student cookie 被歸到後選組別，連帶使答案歸屬與搶答順位看似異常。

根因是同一 browser context 的所有分頁共用單一 `classroom_buzzer_student_session` cookie；後選組別會取代先前 cookie。後端原本始終依目前 cookie 的 session 決定 `activity_id` 與 `group_id`，沒有信任前端 `groupId`，但舊分頁的 React session 標題不會自動得知 cookie 已被其他分頁替換，因此形成顯示身分與權威身分分歧。

本輪修復狀態：

- 學生提交加入分頁預期組別斷言；伺服器仍以 HttpOnly cookie session 為權威，兩者不一致時回覆 `409 STUDENT_SESSION_CHANGED`，不分配 `receive_sequence`、不建立 attempt，並提示使用無痕視窗或不同 browser profile。
- 權威 snapshot 若顯示目前 session 組別與分頁原組別不同，學生 UI 立即顯示警告並停用答案輸入／提交。
- HTTP snapshot 套用 revision guard，延遲返回的舊 snapshot 不再覆蓋較新的 Socket.IO 狀態。
- 老師即時提交、老師 CLOSED 結果及學生目前提交時間統一顯示 Asia/Taipei 的 `YYYY/MM/DD HH:mm:ss`；後端 ISO timestamp 與排名依據不變。
- 自動化測試已重現修正前缺陷，並新增同 context 雙學生分頁、隔離 context 真實排名、重新提交失去原順位、結果／匯出一致及時間格式回歸。這些自動化結果不能取代重新進行真人驗收。
